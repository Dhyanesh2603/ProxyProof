Distributed Smart Attendance System

ProxyProof prevents proxy attendance through high-entropy rotating BLE cryptographic tokens, strict 1-to-1 hardware device binding, and server-side RF proximity validation.

System Architecture

Core Engineering Principles

  • Clean Architecture: Strict layer separation (Controllers → Services → Repositories → DB).
  • Connectionless BLE: Broadcaster/Observer pattern scale to 1000s of students with zero pairing lag.
  • Deterministic Time Slices: HMAC-SHA256 tokens rotated every 5s with bounded grace windows.
  • Reactive Telemetry: WebSockets push real-time attendance events and anomaly flags to dashboard.

Physical Classroom Boundary

At 1 meter, BLE RSSI is approximately −55 dBm. At 8 meters (classroom perimeter), concrete wall attenuation drops signal to ≤ −78 dBm.

Default Threshold: ≥ −75 dBm (Inside Room)

The 8-Step Anti-Proxy Verification Pipeline

1

Student Account & Registration Status

Verifies student JWT token identity and confirms account is in an active, enrolled standing.

2

Hardware Device Binding (Anti-Device Spoofing)

Compares submitted device_uuid against the student's authorized phone hardware UUID stored in devices. Attempt from a friend's phone fails immediately.

3

Session Status Check

Confirms that the session exists and is in the ACTIVE broadcasting state.

4

Time Window Expiry

Checks that current timestamp has not exceeded started_at + duration_minutes.

5

Duplicate Attendance Check

Guarantees that a student cannot be marked present more than once in the same session.

6

RSSI Proximity Threshold Validation

Rejects stray BLE packets detected through doors or windows (e.g. RSSI −84 dBm < −75 dBm cutoff).

7

Cryptographic Rotating Token Verification

Re-computes HMAC-SHA256 signature using the session secret key across the current discrete 5s time slice and tolerance grace window. Forged or forwarded expired tokens fail.

8

Classification & Real-Time Broadcast

Marks PRESENT (or LATE if elapsed time > 15 min), updates device last used timestamp, and broadcasts instant WebSocket notification to organizer dashboard.

BLE Packet Frame Specification

To fit inside standard 31-byte legacy advertising packets without requiring scan responses, ProxyProof encodes its payload into 26 bytes:

Offset Field Type Byte Size Purpose
0..1 Company ID Big-Endian uint16 2 bytes 0x5050 (ASCII 'PP') identifier
2..5 Session ID Big-Endian uint32 4 bytes Unique database session ID
6..9 Window Index Big-Endian uint32 4 bytes Epoch time index: floor(ts / 5)
10..25 HMAC Token ASCII string 16 bytes 64-bit truncated HMAC-SHA256 signature

Interview & Evaluation Defense Guide

Q1: Why did you choose connectionless BLE advertising instead of Bluetooth GATT pairing? ▼
Traditional Bluetooth GATT pairing requires a master-slave connection handshake taking 2 to 5 seconds per device. Most mobile Bluetooth radios support only 7 to 8 simultaneous connections. In a lecture hall of 200 to 500 students, GATT would fail catastrophically. By using connectionless undirected advertising (Broadcaster / Observer pattern), the instructor's device broadcasts to unlimited passive listeners simultaneously with zero connection latency.
Q2: How does ProxyProof prevent a present student from forwarding the token via WhatsApp to an absent student? ▼
Two independent security barriers prevent this: 1. Strict 1-to-1 Device Hardware Binding: Even if the absent student enters the token, their device UUID does not match their registered phone. The request is immediately rejected. 2. Time-Windowed Ephemeral Tokens: The token rotates every 5 seconds. By the time a student takes a screenshot, sends it via messaging app, and the receiver enters it, the token window has expired.
Q3: What happens if a student is standing just outside the classroom door? ▼
Radio waves attenuate through solid barriers according to the log-distance path loss model. A typical classroom drywall or concrete door attenuates the 2.4 GHz BLE signal by 10 to 18 dBm. While a student inside the room observes an RSSI of −60 to −70 dBm, someone outside experiences ≤ −82 dBm. The backend rejects any attempt below the configurable threshold (−75 dBm default).
Q4: How do you handle clock drift between the student's phone and the backend server? ▼
ProxyProof uses a bounded discrete window indexing algorithm: window_index = floor(timestamp / interval). The verification engine checks candidate window w, previous window w - 1, and w + 1. This allows a deterministic tolerance grace window of 1 interval (±5 seconds), absorbing network latency and NTP clock drift while strictly rejecting old replays.
Q5: How does the system scale to 1000 simultaneous students entering a lecture hall? ▼
The backend is stateless and horizontally scalable behind Nginx or Envoy. Active session secret keys and recent token nonces are cached in Redis with sub-millisecond lookups. Concurrency benchmarks in scripts/load_test.py demonstrate sub-15ms p95 latencies and high throughput across 1000 simulated concurrent students.
